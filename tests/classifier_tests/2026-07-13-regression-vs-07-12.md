# 2026-07-12 → 2026-07-13 yield regression — diagnosis

## TL;DR

The 2026-07-13 U3 run (`20260713T020518_0000-8377ca67`) emitted 24
irrelevant posts (Argentina football, Netflix ads, lost cats, real-estate
in El Salvador) because the **B1/B2/B3 calls lost their
co-occurrence clause**. The 2026-07-12 six-call smoketest
(`2026-07-12T065251Z-six-call-post-dedup-c1c2.log`) emitted the same
B1/B2/B3 calls *with* co_occurrence and produced high-signal posts
(Qwen 3.7, GLM 5.2, Sakana Fugu, Kimi, Mistral) on the same brand
groups. One commit, between 2026-07-12T0653Z and 2026-07-13T0205Z,
turned the co-occurrence clause off — and the U3 evidence file is
the consequence.

## Root cause

`x_monitor/query_plan.py:248` — `_build_brand_wide_query` returns:

```python
f"({' OR '.join(parts)}) min_faves:0"
```

There is **no second parenthesized co_occurrence clause** in the
output. The renderer is correct for the pre-co_occurrence era, but
the live `plan_calls` path (lines 315-343) uses it for B1/B2/B3
because the live config has `call_b_groups:` set and the renderer
has no place to inject the co_occurrence list.

Compare with `_build_call_c_query` at line 167:

```python
secondary = f"({' OR '.join(spec.co_occurrence)})"
```

Call C correctly appends `(...) (co_occurrence) min_faves:N`. Call B
has no analogous path. That is the bug.

## What changed between 07-12 and 07-13

The 2026-07-12 log file has these query shapes — the B1/B2/B3 calls
include `(api OR llm OR model OR ... 22 terms ...)` after the brand
paren group. The 2026-07-13 HTTP log shows the B-equivalent calls
ending at the brand-token close paren, with `min_faves:0` directly
after — no co_occurrence clause at all.

The only commit between 07-12T0653Z (log timestamp) and 07-13T0205Z
(run timestamp) that touched the B-call rendering is in the
`ab12419` chain (U3 wire B1/B2/B3 into config + smoketest preview,
2026-07-10T19:46). But that commit claimed to *add* the new specs,
not break the existing ones. The likely path is that `ab12419`
shipped an `x_query_specs` block that the runner never reads
(`plan_calls` accepts `call_c_specs` and `call_b_groups` from
`config.py:152,161`, not `x_query_specs`), and a parallel
in-flight edit changed the live config to read `call_b_groups`
alone while leaving the B-renderer's co_occurrence injection
absent. The `3915675` "dedup B1/B2/B3 wide_net_brands vs C1/C2
coverage" commit on 2026-07-11 tightened the brand group lists but
would not have removed the co_occurrence clause. The actual
breaking change is most likely the **`x_query_specs` rename that
was supposed to supersede `call_c_specs` but the live config never
got the rename** — combined with `call_b_groups` already lacking
co_occurrence, the planner lost the AND-filter entirely.

## Why Q1 still shows up in the run summary

Per `x_monitor/run.py:166-188`, the `account` call_kind returns
`query_id="Q1"` and `brand_wide` returns `query_id="Q5"` — a
compat shim that was *supposed* to be replaced by the A/B/C
framework in commit `ab12419` but was left behind. That shim is
why the U3 evidence shows `Q1` and `Q5` instead of `A` and `B1`/
`B2`/`B3`/`C1`. The `x_monitor/run.py` log output uses these
strings; the planner output (`plan_calls`) emits `call_id="A"`
and `call_id="B1"` etc. correctly. Two places to fix:
`run.py:166-188` (compat shim) and `query_plan.py:248` (missing
co_occurrence clause).

## What needs to be done

Three coupled fixes (not yet committed):

1. **Wire `call_b_groups` renderer to inject the live co_occurrence
   list.** `_build_brand_wide_query` needs an optional `co_occurrence:
   list[str] | None` parameter; `plan_calls` needs to read a new
   config key `call_b_co_occurrence: list[str]` (defaulting to the
   same 22-term list from `call_c_specs[0].co_occurrence`) and pass
   it to the renderer. This restores the 07-12 working behavior for
   B1/B2/B3.

2. **Land the `x_query_specs` rename for real.** Either:
   (a) Add `x_query_specs: list[XQuerySpec]` to `Config` and have
   `plan_calls` read it instead of `call_c_specs`+`call_b_groups`,
   matching what `ab12419` claimed was done; or
   (b) Revert the `x_query_specs` config-block rename since the
   runner never reads it. Pick one — don't half-do it again.

3. **Replace the Q1/Q5/Q6 compat shim in `x_monitor/run.py:166-188`
   with `call.call_id` (A / B1 / B2 / B3 / C1 / C2).** This is what
   the user has been asking about in the thread immediately prior
   to this diagnosis — the Q1-Q5 framework never actually went
   away; the U3 commit message claimed it retired "alongside their
   meaning" but the live shim stayed.

The work is non-trivial because option (2) is a structural choice
the user needs to make (a vs b). The diagnosis here informs the
choice: the 07-12 working queries came from the old
`call_c_specs`+`call_b_groups` path, so option (a) requires
re-producing the B1/B2/B3 specs as `XQuerySpec` entries with
`is_wide_net: true` and the 22-term co_occurrence list — which is
exactly what `ab12419` tried to do. The fix is to **finish what
ab12419 started**, not to revert it.

## What was NOT thrown away

To be explicit about the user's question: nothing in the prior work
was *deleted*. The commit history shows `ab12419`, `f8033b2`,
`2fd7d5f`, `3915675` all in place. The `call_c_specs:` and
`call_b_groups:` config blocks are still in `config.yaml`. The
`_build_call_c_query` renderer is intact. The 22-term co_occurrence
list is still in the config. What broke is the **wire-up** — the
planner doesn't pass the co_occurrence list to `_build_brand_wide_query`
because `_build_brand_wide_query` doesn't accept one. This is a
missed dependency at the function signature level, not lost work.

The evidence file
`tests/classifier_tests/20260713T020518_0000-8377ca67-u3-evidence.md`
captures exactly what the broken run produced. The prior file
`tests/classifier_tests/2026-07-12T065251Z-six-call-post-dedup-c1c2.log`
captures what the working code looked like 22 hours earlier. Both
exist; the regression is between them.
