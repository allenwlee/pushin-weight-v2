# Why V4 Flash 0731 behaved differently from V4.1 Flash

## Finding

The experiment changed three things at once: model generation, inference provider, and output-format path. The observed difference is therefore not evidence that one nominally similar “Flash endpoint” is mysteriously broken. The direct control is the new V4.1 model served by DeepSeek itself. The cheap candidate is the retired July 31 V4 model served from open weights by a third party.

The largest latency cause is confirmed: OpenInference serves 0731 much more slowly than DeepSeek serves V4.1. The largest completeness cause is also confirmed: sending `response_format` to 0731 caused most of the omissions. Removing that parameter nearly completed the same 20-post call; changing only the FP8 provider to DeepInfra completed every required slot.

## 1. They are different model generations

The direct request used the legacy name `deepseek-v4-flash`. DeepSeek's September 10 change log says that this name now routes to **DeepSeek V4.1 Flash** because the earlier V4 Flash model has been retired. V4.1 is not a minor 0731 checkpoint revision:

- V4 Flash 0731 is a 284B-parameter mixture-of-experts model activating about 13B parameters per token.
- V4.1 Flash is a new 552B Causal Encoder-Decoder model activating 8B parameters during input processing and 16B during output generation.
- DeepSeek reports that V4.1 was trained from scratch on a 45T-token multimodal corpus and uses a new post-training data pipeline.
- V4.1 specifically targets faster input-heavy inference and more reliable long-running task completion.

Sources: [DeepSeek API change log](https://api-docs.deepseek.com/updates/), [V4.1 model card](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash), and [0731 model card](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash-0731).

## 2. They were served by different infrastructure

| Run | Model/provider | Batch | Calls | Observed latency | Approximate output throughput |
| --- | --- | ---: | ---: | ---: | ---: |
| V4.1 control | V4.1 through DeepSeek's direct API | 20 posts | 4 | 5.77–5.90s per call | 324 output tokens/s across serial calls |
| Scored 0731 | 0731 through OpenInference FP8 | 5 posts | 16 | 9.34–27.47s per call | 21 output tokens/s across serial calls |
| R114 diagnostic | 0731 through OpenInference FP8 | 20 posts | 1 | 49.31s | 20 output tokens/s |
| R115 diagnostic | 0731 through DeepInfra FP8 | 20 posts | 1 | 15.12s | 95 output tokens/s |

OpenRouter's current provider table reports about 19 tokens/s for OpenInference, matching the observed 20–21. The slow result is therefore normal for that bargain route rather than unexplained network delay. DeepInfra was 3.3 times faster in the controlled 20-post probe, although it charged $0.001129 versus OpenInference's $0.000422 for that call.

Source: [OpenRouter's 0731 provider table](https://openrouter.ai/deepseek/deepseek-v4-flash-0731).

## 3. The output-format paths were different

The V4.1 control did **not** use an API-native `response_format`. Its JSON schema was ordinary text appended to the system prompt, and DeepSeek returned complete JSON voluntarily.

The initial 0731 trials used OpenRouter's native `response_format` path:

- R110 used a strict dynamic schema and repeated the first case identifier for all 20 results.
- R111 used fixed slots with a strict schema and collapsed nearly all decisions to the same contradictory classification.
- R112 used lightweight `json_object` mode; semantic variety returned, but the model stopped normally after 11/27 decision slots and 9/20 post slots.

R114 removed only `response_format` from the R112 request. Model, provider, 20-post input, prompt, sampling, seed, reasoning setting, and token ceiling stayed fixed. The response improved to 27/27 decision slots and 19/20 post slots. It ended with `finish_reason=stop`, so neither the earlier omission nor the R114 omission was caused by the 6,000-token ceiling.

R115 kept that no-format request and changed only the serving route and matching price cap from OpenInference FP8 to DeepInfra FP8. It returned 27/27 decisions and 20/20 post slots. One decision placed `business_finance` under `audience_topics`, so the response was complete but still failed the semantic contract.

DeepSeek's official V4 encoder turns `response_format` into an additional “strictly adhere” schema block in the prompt. OpenRouter documents that structured-output implementation and enforcement vary by provider. Consequently, `response_format` was not a harmless transport option in this model family; it materially changed the instructions the model saw. Sources: [DeepSeek V4 encoding](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash/blob/main/encoding/encoding_dsv4.py) and [OpenRouter structured outputs](https://openrouter.ai/docs/guides/features/structured-outputs).

## What remains uncertain

- The V4.1 and 0731 semantic scores are not a clean weight-only comparison. V4.1 used temperature 0 and schema-as-text, while the customized 0731 run used temperature 1, fixed slots, and a lighter output contract.
- DeepSeek does not attest the quantization used by its managed V4.1 API. Both controlled 0731 provider probes used FP8, so the OpenInference-versus-DeepInfra result is not explained by a quantization change.
- R114 and R115 are one-call diagnostics. They establish the causal direction for this packet but do not yet establish batch reliability over the entire 40-post cohort.

## Practical conclusion

The earlier statement that 0731 “cannot handle 20 posts” was too broad. The evidence now says:

1. OpenInference is intentionally a very cheap, slow route.
2. Native `response_format` caused most of 0731's completeness failure.
3. With schema instructions in plain prompt text, 0731 nearly completed 20 posts on OpenInference and completed all slots on DeepInfra.
4. A full four-call, 40-post DeepInfra/no-format run is the next fair viability test before rejecting 0731 or moving to another model.

The diagnostic artifacts are `.context/u18/fresh40-v4-0731-no-format-r114-v1/` and `.context/u18/fresh40-v4-0731-deepinfra-r115-v1/`. They are offline evaluation evidence only and made no database or production changes.
