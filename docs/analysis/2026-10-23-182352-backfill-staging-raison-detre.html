Running July implementation

Up to 20 HTTP calls → Wait for the group → Archive response bodies → Serial Post writes to production

Benefit: saved response bodies can be replayed after interruption without another paid search.

Cost: raw bodies and Posts overlap in storage; one slow request delays a group; ingestion must share production writer access with the harvester.

New staging implementation

Up to 20 HTTP calls → Process ready pages → Posts + receipts in staging → Later bounded promotion

Benefit: continuous processing and a separate staging database; no permanent full search-response copy in this mode.

Tradeoff: losing an uncommitted in-memory response can require a paid refetch. Promotion adds a separate bounded transfer step. Real-provider throughput and a production pilot remain unmeasured.

The design’s reason for existing

  1. Keep time-sensitive acquisition moving. Historical search already omits some matching Posts. Finishing collection earlier matters, but this design cannot recover Posts that X filters out.
  2. Protect live harvesting. Staging collection uses a separate database. Production promotion still yields to the live writer; this is not permission to remove locks.
  3. Avoid retaining every response twice. Posts and required candidate/profile evidence remain. Physical request receipts say what was sent and received; a body hash is not a replayable body.
  4. Reuse the harvester. Parsing, eligibility, attribution, Post storage and rare admission remain shared. The change is transport scheduling, storage destination and later transfer.
Why not twenty database writers? The current code locks the same job/run rows and uses shared process settings for each page. Twenty independent writers would require more redesign. The implemented version uses twenty HTTP workers and one protected database writer. No production throughput improvement has yet been measured.
