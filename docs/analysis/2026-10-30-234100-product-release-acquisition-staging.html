What the system is intended to do

Start from a saved post or another saved source, retain a pending release dossier, and look for a small set of specific source records. A repository match can identify a Product, while confirmation of an announcement requires evidence that the publisher controls the announcing source. Captured source values retain their observation time. No new language-model call is used by routine detection.

Storage and safeguards

One reusable detector-state row per saved Post records progress and bounded retries. A saved HF observation with no reviewed Product mapping retains a waiting collection scope; a later eligible contract can reuse the observation without fetching it again. Native-only and Product-specific measurements remain separate. The background feature remains disabled in staging until explicitly activated.

On the staging revision, a finite job processed the saved OpenZero post twice: each pass selected one candidate, its dossier stayed at 23 claims, both dossier reviews were preserved, and no new provider request was made. Its exact HF observation is waiting for a reviewed contract; an immediate second check selected nothing during the six-hour wait. A first attempt used the restricted web role and failed to read the evidence archives; the two resulting staging cooldowns were recovered using the job service. A separate access check confirmed that the staging headline worker can read those archives and insert detector-state rows, with the feature flag off. Staging has no active reviewed HF metric job, so this test does not claim a real late-contract projection has occurred there.

Source records and claims are retained in existing collection and EventDossier storage. The branch adds six tables in total, including the detector state, and no new JSON column. The final index for due measurement work is created concurrently on the existing collection scope table.

The automatic source fetches implemented here cover targeted Hugging Face and GitHub records. A GitHub improvement deployed to staging reuses an existing reviewed, dedicated Product mapping when the captured repository and owner match; it does not confirm an announcement. This rule passed local tests, but staging has no real reviewed dedicated GitHub mapping with which to exercise it. The deployed measurement path can project captured GitHub metrics under an eligible reviewed contract, or wait until one exists. A rollback-only staged simulation verified the waiting path without a real provider call; staging has no active reviewed GitHub metric job, so real Product projection is supported by local tests rather than staged evidence. Unknown GitHub-only Products can be retained provisionally when an exact source-bound repository, matching owner profile and direct project announcement establish the narrow identity rule; other cases remain unresolved. Public GitHub release observations now have their own durable detector handoff, behind the disabled background flag. A rollback-only staging simulation created two dossiers for two public releases and reused them when the same releases were captured again; it did not use a real provider response. Other provider collectors and broader publisher-site acquisition need further integration.

For source-reported HF base models, acquisition follows at most five exact parent repositories per metadata response and keeps additional reported names as evidence. For OpenZero, the original archived metadata and a later exact Qwen capture support a new claim with a parent Product reference. The existing dossier grew from 24 to 25 claims; both reviews and the current review remained unchanged. Replaying the same evidence made no request or additional claim. This is a source assertion, not a reviewed taxonomy relationship.

A later rollback-only staging test fetched the DeepSeek Harness release records with three live GitHub requests and replayed three public releases through the source detector. Three pending dossiers were created and then rolled back. The test synthesized the publisher's inventory response to restrict the replay to this one repository, and the collector reported partial coverage at its item limit. This verifies real release response handling, not persistent live catalog collection or automatic identity for an unknown GitHub-only Product.

A rollback-only staging test used simulated GitHub responses to detect a release before a dedicated Product mapping existed. The later review automatically recorded reconciliation work; an explicitly invoked bounded drain linked the saved repository and release observations to the Product and reused the original dossier without another provider request. The background feature remains off, so the test did not activate a live worker.

A second rollback-only test used a synthetic announcement and simulated GitHub responses for an unfamiliar project. When the post explicitly named the repository project and its author matched the profile's reported X handle, the system created a provisional Product, linked its repository observation and created a measurement subject. It did not confirm a release; replay made no additional provider request. The rule currently covers only narrow wording, and a current profile handle does not prove historical account control.

A later staging test also exercised “excited to announce”: the synthetic direct post created a provisional Product, while a retweet did not acquire a Product claim. This test used simulated responses and rolled back its writes; it does not establish accuracy across other languages or phrasings.

To check a delayed source, a rollback-only test gave the exact DeepSeek Harness lookup a simulated 404, then retried it against the live GitHub API. The retry captured a real 200 response in the same run; another replay made no provider call. The retry time was advanced only within the test transaction. This validates the retry mechanism but does not claim a historical 404 for this repository.

Using the real saved Nanbeige capture and simulated publisher/metric authority, a rollback-only test projected its 12,178 downloads and 787 likes with the original observation time and no new provider request. The first attempt exposed a missing follow-up marker for this older capture; a separate staging job restored that single marker and safely repeated the integration. It now waits for a genuinely reviewed contract. The test did not establish publisher ownership or leave approved measurements behind.

A subsequent staging inventory found three exact Hugging Face or GitHub release-acquisition captures, and all three have a measurement follow-up marker. This count excludes expanded metadata, lineage captures and other source types.

The GitHub refinement is deployed to staging and passed seven local PostgreSQL response tests. It distinguishes explicit private, unauthorized and rate-limited outcomes. A 403 remains ambiguous between access denial and rate limiting, and a 404 remains ambiguous between missing and private; the original HTTP status is retained. A database-free check of the deployed classification passed all seven simulated responses without provider requests. Two earlier staging simulations of the full write path stalled or timed out on a synthetic Post insert; neither is counted as a pass, and no synthetic posts remained. The saved-request write path passed locally.

Verification and limits

The local projection and release-pipeline suite passed 108 tests; focused queue and measurement tests passed after later changes. A separate existing harvest test fails because the unchanged configuration uses a 24-hour lookback while the test expects at most one hour. The shared local test database was restored to its previous migration level. One remote test-import formatting failure was corrected; the latest remote check results are separate from these local tests and can be read on the pull request.

The read-only production health check did not pass. At the first observation all 20 selected posts were freshly pending. Thirty minutes later, one was complete and 19 were unhealthy because both English and Chinese commentary were missing. Language detection was present for all 20 posts, and the required Chinese translation was present for all 18 applicable posts. The exact same IDs were checked both times. These release changes are not deployed to production; the check does not establish the cause of missing commentary. No production write, provider call or model call was made by the check.

Confirmation, availability and first use remain separate. Missing repositories, unfamiliar publishers, low attention and missing Product mappings do not establish fraud. This report does not assert complete coverage of every release in the database or a measured miss rate.
