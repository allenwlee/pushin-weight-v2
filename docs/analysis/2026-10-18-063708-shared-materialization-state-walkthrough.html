One shared table to track precomputed datasets

Replace the homepage-only state row with a keyed lifecycle table. Homepage counts can use it first; future ChartEngine aggregates can use separate rows with their own freshness and refresh policy.

home_count_snapshot(id=1) becomes the proposed materialization_state(dataset_key). The row describes the current publication of one rebuildable dataset; it is not one row per chart, article, daily run or time window.

Relative to the currently deployed baseline, the feature still adds one managed table and one native materialized view. Relative to the existing candidate, this is a replacement/generalization of its one new table, not a second state table. No production table is renamed by this proposal.

A concrete shared Django model supplies one physical table. An abstract Django base class alone would leave each consumer creating another physical table and would not meet the shared-storage goal.

Source records

Posts, attribution and flags; future datasets declare their own actual dependencies.

Typed derived data

home_brand_time_counts retains count rows and its own SQL definition.

Shared lifecycle row

materialization_state records coverage, generations and publication time.

Relationship: one registered dataset key maps to one current state row and an allowlisted implementation. That implementation may read many aggregate rows. This association is an application/trigger contract; there is no foreign key from the native materialized view.

Proposed materialization_state columns

Only the identifier changes from the candidate's six-column table. These are proposed Django field definitions, not generated SQL types or deployed columns.

Physical column proposedType and nullabilityMeaning
dataset_keyProposed CharField(max_length=160), primary key; non-nullStable dataset and definition version, e.g. home.brand_time_counts.v1. Replaces id=1.
source_generationPositiveBigIntegerField; non-null; default 0Per-dataset counter advanced by relevant source changes.
published_generationPositiveBigIntegerField; nullableCounter represented by the committed aggregate.
dirty_sinceDateTimeField; nullableEarliest source time affected since publication. NULL does not mean no source records.
cutoffDateTimeField; nullableExclusive upper coverage boundary of saved history. Each adapter defines its clock/grain.
refreshed_atDateTimeField; nullableWhen this successful publication finished, rather than the measurement boundary.

Constraints retained: published_generation IS NULL OR published_generation <= source_generation; published generation, cutoff and refresh time are either all NULL or all non-NULL. Replace singleton id=1 with a nonempty primary dataset key. No foreign keys are proposed.

Identity: a key includes a definition version. Changes in calculation, eligibility or grain need an explicitly versioned key/migration or deliberate invalidation/rebuild; an old state row must never silently certify a new calculation. Only registered, shared datasets get rows. Arbitrary editor filter combinations do not each create a new key or materialized view.

A source correction and the next refresh

  1. Register and initialize: deploy a reviewed dataset definition and provision its state row. Preserve the tested missing-state barrier: previously untracked source writers must finish before committed initialization and counting. If state is unavailable, readers use the exact fallback.
  2. Invalidate only affected keys: a historical post-brand correction advances the home key's source_generation and lowers dirty_since. It does not touch a future HF metric or chart key unless that dataset actually depends on that source.
  3. Read safely: for home counts, a generation mismatch with dirty_since < cutoff requires exact-source fallback. Current-day changes can stay in the exact live tail. Other adapters must supply their own valid coverage rules.
  4. Refresh: acquire the stable per-dataset maintenance lock, capture the generation, build the typed aggregate, and conditionally publish against that same generation. Aggregate refresh and successful publication remain atomic. Missing-state setup is committed earlier.
  5. Source changed while counting: do not publish; roll back the refresh and preserve dirty state. A failed refresh never advances the publication markers.
  6. Publish: on success set published_generation, cutoff, refreshed_at and clear dirty_since. A coherent reader checks health and reads values within one SQL snapshot.

A small code registry maps an approved key to its refresh handler, dependency projections, clock/grain, stable lock identity, readiness rule and fallback. Do not store arbitrary SQL for execution or accept untrusted relation names. Per-dataset locks and counters avoid serializing unrelated datasets; shared dependencies must still define lock order. The homepage can keep its current lock identifier.


Where G2 and ChartEngine fit
The current G2 plan explicitly proposes SummaryRun for requests, access scope, execution and immutable completed results. Its result_hash, spec_hash and frozen population/manifests bind article, chart and prediction inputs. The existing G3 local chart work saves immutable settings/data with edition evidence and OriginalContent provenance. These are distinct record meanings.
Share the freshness mechanism; preserve the frozen evidence.
A SummaryEngine job may read an eligible aggregate through the shared measurement interface when its definition, dimensions, counting unit, time grain and access scope exactly match. It then freezes the actual result and source identity. ChartEngine renders that saved result. A later aggregate refresh cannot rewrite the article's evidence.

Home count totals are post-brand memberships. A chart of unique posts across brands, classification shares, products, retweet/reply filters or financial/benchmark values may need other dimensions and denominators. Registering state never makes those queries equivalent. Unsupported combinations keep exact readers, with unknown/missing values preserved. Chart styling changes do not create a new data snapshot.
Freshness schedules belong to each adapter: daily closed history is appropriate for the selected homepage comparison; it is not a rule for every future chart. A saved result remains immutable regardless of the adapter's cadence. A live aggregate is not an historical as-of archive.


What changes before this can ship
Current verified candidate ef1788f5 does not implement this proposal. The owner requires reusable storage; the key/name and minimal adapter design here are recommendations. The existing production endpoint and staging-access prerequisite remain unchanged.
  1. Update the existing plan and add caller-level failing regressions for independent dataset keys, then generalize the model, schema, SQL triggers, refresh/read/cache consumers and maintenance command.
  2. Retain the unique view index, initialization race repair, transaction coherence, timeout and exact-fallback behavior. Source invalidation must target only registered dependent datasets. Fake second-dataset coverage tests registry isolation without adding a speculative production view.
  3. Prove changing one key does not dirty, publish or lock the other. Test concurrent source correction, missing rows, failed refresh, midnight rollover and definition mismatch. Preserve native migration forward/reverse/reapply and source data.
  4. Update staging exclusion/export grants, restore/scrub guards, schema reference and operational runbook for the shared relation. Preserve exporter restrictions and never copy environment-local publication state.
  5. Run the affected strict PostgreSQL/caller regression net and exact-candidate hosted/browser/release checks. Reuse unaffected evidence only with valid code/fixture/environment identities. No old green candidate certifies changed publication SQL.
