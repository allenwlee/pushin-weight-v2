## 10. Pending operator actions

The previous version of this doc assumed U1 + U3 had been applied. They have not. Before this DB state matches the schema-modernization-batch plan body, the operator must:

1. **Run the U1 + U3 seed scripts against prod.** Both scripts are idempotent (`INSERT OR IGNORE`). The 88 `brand_keywords` rows that are already present will not be touched. The 12 brands / 11 companies / 11 hf_orgs rows are also `INSERT OR IGNORE`-safe — the U3 script will add the 9 NEW brands + 9 NEW companies + 11 NEW hf_orgs rows.
2. **Apply migrations 012 → 022** in order, on the worktree branch (`feat/schema-modernization-batch` HEAD `4c9d8a0`). The `Store.apply_migrations()` runner is idempotent — already-applied versions are skipped. **However**, the seed scripts assume the pre-019 schema (`signal_keys` table, no `post_type_keys`). Migration 022 drops `signal_keys`/`signal_labels`/`posts_brands_signals.signal_id`. Therefore:
   - If seeding BEFORE applying 012-022: U1/U3 run against current prod (TEXT-PK, `signal_keys` present). All fine.
   - If applying 012-022 BEFORE seeding: U1/U3 work but produce different intermediate shapes (e.g., `post_type_keys` instead of `signal_keys`). U3 doesn't touch `posts_brands_signals`, so 022's kill doesn't conflict.
   - **Recommended order:** apply 012-022 first, then run U1 + U3. The worktree branch already has the U1 + U3 commits at HEAD; merge in that order.
3. **Spot-check the seed state after merge** by re-running `python scripts/2026-06-25-004-populate-brand-search-terms.py --dry-run` (idempotency check) and `python scripts/2026-06-25-005-seed-companies-brands-from-csv.py --dry-run` before the real run.
