# Using Sol labels to train a small classifier

Status: researched option under deferred KTD48; teacher transport selected by the owner as OpenRouter, with a conditional direct-OpenAI option. The proposed training experiment has not started.

Sol can label existing posts and those labels can train an embedding-based classifier such as SetFit, or a smaller language model. This transfers task-specific decisions into a cheaper model; it does not transfer Sol's general reasoning ability. The six owner-approved additions make Sol a promising teacher, but do not establish that all its remaining predictions are correct.

## Owner-selected labeling route

Use Sol through OpenRouter with application-controlled API messages. The owner declined subscription-backed Codex labeling because it introduces additional agent instructions and session context. Codex may still prepare inputs, code and reports; its sessions and subagents are not the teacher inference route.

Switch to the direct OpenAI API if a verified comparison shows lower total cost for equivalent model identity, prompt, source/brand evidence, reasoning effort, output schema and token settings. Include applicable discounts, funding fees, cache reads/writes, billed reasoning/output, and batch prices when the turnaround suits this offline job. Preserve route and model provenance and verify that the direct adapter retains the intended request and output behavior. This decision does not claim either route is currently cheaper, expand the proposed experiment's budget, or modify the frozen OpenRouter trials.

## Proposed first experiment

**Next evaluation precedes this training proposal:** The owner is currently reviewing the [fresh 45-post packet](../analysis/2026-09-15-121342-u18-fresh-45-review-packet.md), cases L45-01 through L45-45, and has selected a Sol evaluation through OpenRouter once that review is supplied. Reserve those posts and known duplicate/thread groups from the proposed training pool, prompt examples, and tuning. Owner answers stay outside Sol's input. Freeze the candidate using existing rules and development cases; if new review answers later influence tuning, record that this cohort has been consumed. This rare-case challenge set has seven source languages and does not estimate whole-database accuracy. The earlier 45-case review remains complete.

1. Settle the already accepted shared input and prompt corrections first, especially target-brand meaning, reviewed author affiliation, quote versus author stance, overlapping labels, and primary-post retention. Freeze the teaching taxonomy and prompt. Existing R106 labels cover the older six axes; they do not supply new Audience Topics, Geopolitical modes, or Untracked Brand Promotions automatically.
2. Use existing real database posts for the initial training pool. A bounded starting proposal is 2,000 post-brand examples, combining a sample in the database's actual language mix with deliberate rare-label and cross-brand cases. The size is an experiment proposal, not a claim of statistical sufficiency. Track support for each label/language and expand only where the learning results justify it. Preserve source text, quote/parent context, target brand, reviewed affiliation, language, taxonomy/prompt/model versions, and label provenance.
3. Split by source post, thread and near-duplicate group before labeling or training so variants and brand rows from the same source cannot leak across training and evaluation. Keep a separate unseen evaluation sample with natural frequencies, plus explicit rare-case diagnostics. The current 45 examples remain consumed development evidence; never call them unseen test accuracy.
4. Have Sol propose all applicable labels for each training example. Store the label and its available evidence as a model suggestion, separately from owner-confirmed decisions. Do not fabricate probability scores or treat Sol's own confidence as calibrated. Do not use blanket absence as a reliable negative when the source evidence is missing. No need for the owner to label thousands of posts or redo the completed 45-case review; later targeted spot-checks are optional and their absence limits claims of human-verified accuracy.
5. Start with a multilingual embedding encoder and inexpensive prediction heads: independent yes/no outputs for overlapping labels and constrained outputs for single-choice axes. A frozen-encoder baseline can precede SetFit fine-tuning so the benefit of adapting the encoder is measured. SetFit supports multiple labels; a single shared embedding with all the project's mixed output families requires explicit head/training integration rather than assuming the library implements our complete contract out of the box. Both teacher and student must receive the evidence available at runtime. A target-brand input marker alone is not proof of learned brand attribution; test same-post/different-brand cases explicitly.
6. Measure correct labels, extra labels, missed labels, complete-row validity, language/brand/rare-label slices, CPU memory/latency, and serving cost. A classifier emits a fixed set of scores rather than generating an optional list, eliminating omitted-output-field behavior, but it can still score a valid secondary label too low. Set thresholds with separate development data. Teacher-labeled unseen evaluation measures agreement with Sol; it does not independently establish truth or superiority over the teacher.
7. If the embedding model cannot learn the more contextual judgments, reuse the labeled dataset to test fine-tuning a smaller generative model. Keep any fallback LLM calls, retraining frequency, and paid hosting as separately measured options, not automatic additions. A later taxonomy change requires a versioned labeling/training update; the trained model will not acquire the change from an edited prompt alone.

## Cost interpretation

The saved Sol-low R106 trial cost $0.136168 for 45 post-brand examples, or about $3.03 per 1,000 at that trial's observed discounted provider price and token profile. A similarly shaped 2,000-example labeling run would extrapolate to about $6.05 before the account-funding fee, training, hosting, additional evidence output, or a larger taxonomy. This is an estimate from a small run, not a quote or approved spend. Sol xhigh cost $0.609898 for the same 45 examples and still produced more extras; it is not automatically the preferred teacher setting. Once trained, a locally served embedding classifier makes no generative API call for ordinary inference, but compute/hosting and periodic relabeling/retraining remain real costs. A tenfold reduction and the $150/month full-LLM budget require measured end-to-end economics, including the translator and other remaining calls.

## Evidence

- [Hugging Face/Argilla authors' worked example](https://huggingface.co/blog/sdiazlor/custom-text-classifier-ai-human-feedback) uses LLM annotations plus human feedback to train a SetFit classifier. Its simpler sentiment task establishes feasibility, not accuracy on this project's axes.
- [SetFit multi-label documentation](https://huggingface.co/docs/setfit/how_to/multilabel) documents one-vs-rest, multi-output and classifier-chain heads.
- [SetFit architecture](https://huggingface.co/blog/setfit) describes fine-tuning a Sentence Transformer and training a classification head on its embeddings.
- [Distilling Step-by-Step paper](https://aclanthology.org/2023.findings-acl.507/) demonstrates using model-generated labels and explanations to train smaller task-specific models. Explanation training is optional here and would add preparation cost; no private reasoning trace is assumed available from R106.
- [SetFit DistillationTrainer documentation](https://huggingface.co/docs/setfit/how_to/knowledge_distillation) uses a trained SetFit teacher. Sol JSON labels would feed ordinary supervised training; they cannot simply be passed as a remote Sol model to that trainer.
