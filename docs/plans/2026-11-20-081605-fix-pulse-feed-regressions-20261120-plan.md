## Plain-English Summary

Restore timely feed enrichment and make the release pipeline tolerate supported partial results. The production classifier currently processes individual posts in batches and delays publication until the batch returns. Invalid release data can prevent independent feed classifications from being saved, and duplicate identical assertions can reject an otherwise supported finding. Publisher attribution also needs evidence-based verification.

Preserve source evidence, release decisions and the running harvest. Verify behavior with local regression tests, measured workload checks, review, and live production observations. The owner selected direct production delivery.

## Execution and verification

- Reproduce and repair latency, classification independence, duplicate assertion handling, and evidence-supported publisher resolution, preserving historical and concurrent behavior.
- Use branch-specific empty PostgreSQL fixtures and existing tests. Prove complete and incomplete outcomes, retries, lease safety, no fabricated empty release result, and existing caller behavior.
- Inspect the full diff, review regressions, run applicable browser and configuration checks, and compare production health after release.
- Do not interrupt live harvest or unrelated workers. Do not ship the separate official-account response-recovery experiment.
- Independent review identified conflicting publishers, incompatible product categories, existing identity claims, and release-only retries as regression cases. Preserve conflicting evidence rather than attaching a different model, and permit a valid feed result alongside an earlier independent release result.
- The HF fallback is a catalog-based inference from a uniquely matching, specifically named model; it cannot prove global name uniqueness. Named publisher evidence takes precedence and ambiguous catalog matches remain unresolved.
- Six simultaneous Pulse classifications remain subject to the continuous worker's existing per-batch call limit. The prior dollar-limited window has expired; continuous mode does not use that window. Future window-bound runs must use a fingerprint covering the new concurrency. Monitor provider failures and feed latency after rollout.
- During the first deployment, the outgoing worker's concurrent diagnostic writes conflicted while shutting down, causing a batch-level classifier exception. Treat that diagnostic conflict as nonfatal, just like an unavailable diagnostics store; the original per-post failures remain pending for retry.
